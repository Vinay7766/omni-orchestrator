## F1 end-to-end test (2026-11-03)

Problem: prove that one project goes the whole v0.1 way, through the real code of each channel,
with one shared memory: idea in the app, planning to architecture, task list, tool handoff, one
build task created and completed through the MCP server, and the build approved from the extension.

Constraints: must pass in CI on Windows, macOS and Linux (G1) with no network, no model and no
editor; vitest does not type-check, so the test must also pass `tsc` (root `npm run build`); the
app's Rust commands cannot run in the web-view test environment.

Approaches considered:
- A: one test in the app suite (`src/e2e/`) that calls the app's own functions with the existing
  `fakeInvoke` (memfs commands on real files), connects an MCP client to `createServer` over the
  SDK's in-memory transport, and calls the extension's `approvePhase` with a scripted person.
  Imports the packages' sources directly, so no build order problem (CI type-checks the app before
  packages build). Main risk: the app's `tsc` now also checks the server and gate sources.
- B: a new `packages/e2e` workspace. Cleaner boundaries, but the app is not a package, so it would
  need path aliases into `src/lib`, a new tsconfig and workspace wiring: more moving parts for one test.
- C: run the built `dist/` server over stdio and drive the real Tauri app (WebDriver). Closest to
  real use, but needs a desktop build and a driver in CI on three platforms; far beyond F1's need,
  and the Rust commands already have their own tests.

Chosen: A, because it is the smallest change that runs every channel's real code in CI, and the
pieces it stands in for are only the ones that cannot run there.

Stand-ins (stated in the test): `byok_complete` (the model) returns scripted answers; `hand_off_tool`
(Rust: writes AGENTS.md and opens the tool, tested in Rust) returns a fixed result; the MCP client
is the SDK client, not a real editor. F2 covers real tools by hand.

Switch if: the app's `tsc` cannot check the package sources cleanly (move to B), or F2 shows a
failure only the built server over stdio would catch (add a stdio run, as `stdio.test.ts` does).

Edge cases tested: each channel's actor is the one recorded (person in the app, the MCP client by
name, the person in the extension); the build cannot be approved while a task is unfinished is
already covered by core; the workflow chart built from the final memory shows every node done.

Test-first note: the code under test already exists (E5-E8), so the test passed on its first run.
To show it can fail, a mutation check made the extension's approve request changes instead; the
test went red ("expected 'changes_requested' to be 'approved'") and the file was restored from git.

Timing (after E10): the MCP server writes its session record in the background, so the test
connects the agent from inside the project after the handoff (as a real tool does), waits for
`sessionRecorded`, checks the record's actor, and closes with `closeServer` before deleting the
folder. The test takes about 1 s alone; it has a 30 s limit for the slower full parallel suite.

Generalisation check: the tool, client and model names are made up; nothing names a real vendor.
Assumptions to confirm: none.
